# BDD Spec: Глобальные идентификаторы и отслеживание локальных изменений

> **Change ID:** `prepare-sync-data-model`
> **Дата:** 2026-09-16

Сводка: спецификация покрывает переход колод и карточек на UUID (включая миграцию существующих данных с сохранением статистики), строковые аргументы навигации, признаки `isChanged` / `revision` / `isDeleted`, персистентный флаг синхронизации в DataStore и ветвление удаления «физическое / мягкое» по флагу. Сетевого взаимодействия в фиче нет — все сценарии описаны в терминах действий пользователя и состояний локальных данных. Краевые случаи смоделированы по аналогии с HTTP-ошибками: невалидные аргументы навигации — аналог 400, отсутствующие записи — аналог 404, сбои DataStore / Room — аналог 500.

## Сценарии

**Миграция схемы и данных**

### S1: Миграция выдаёт существующим записям UUID и сохраняет данные

- **GIVEN** на устройстве работает предыдущая версия приложения: в Room БД есть 2 колоды и 7 карточек с числовыми автоинкрементными ID и накопленной статистикой повторений
- **WHEN** пользователь устанавливает обновлённую версию и запускает приложение (выполняется миграция БД)
- **THEN** приложение открывается без сбоев; каждая колода и каждая карточка получила уникальный UUID; записи не продублированы и не потеряны; пользователь видит те же колоды с теми же счётчиками и той же статистикой повторений; экраны выглядят и работают как раньше

### S2: Миграция пересчитывает ссылки карточек на колоды

- **GIVEN** в старой БД карточка ссылается на колоду по числовому ID (deck_id = 1)
- **WHEN** выполняется миграция схемы
- **THEN** колода получает UUID "X"; ссылка карточки на колоду становится строкой "X" (UUID), а не числом; карточка по-прежнему входит в ту же колоду — счётчик карточек колоды не изменился

### S3: Мигрированные записи помечаются как локально изменённые

- **GIVEN** в старой БД есть колоды и карточки без полей isChanged / revision / isDeleted
- **WHEN** выполняется миграция
- **THEN** каждая мигрированная запись получает isChanged = true, revision = 1, isDeleted = false — записи считаются локально созданными и будут переданы будущей синхронизации

### S4: Краевой случай — миграция пустой БД

- **GIVEN** предыдущая версия приложения, в БД нет ни одной колоды и карточки
- **WHEN** выполняется миграция на новую схему
- **THEN** миграция завершается без ошибок; записи не создаются и не теряются; БД пуста и валидна

### S5: Чистая установка создаёт БД сразу в новой схеме

- **GIVEN** приложение устанавливается впервые, старой БД на устройстве нет
- **WHEN** выполняется первый запуск приложения
- **THEN** Room создаёт БД сразу в новой схеме (UUID, isChanged, revision, isDeleted), путь миграции не выполняется; идемпотентный сидинг создаёт базовую колоду из 5 карточек — каждой записи приложение само генерирует UUID; записи получают isChanged = true, revision = 1; колода видна в списке со счётчиком 5

**UUID и навигация**

### S6: Новые записи идентифицируются сгенерированным приложением UUID

- **GIVEN** приложение запущено, БД создана (флаг синхронизации в любом состоянии)
- **WHEN** через repository создаётся новая колода или карточка
- **THEN** идентификатор записи — UUID, сгенерированный на клиенте; автоинкрементные числовые ID не используются; UUID уникален среди записей того же типа; ссылка карточки на колоду — UUID колоды

### S7: Навигация передаёт идентификатор колоды строкой

- **GIVEN** в списке колод отображается колода с идентификатором "X" (UUID)
- **WHEN** пользователь тапает по колоде
- **THEN** навигация передаёт аргумент deckId как строку "X"; открывается тренировка карточек колоды "X"; внешний вид и поведение экранов списка и тренировки неотличимы от предыдущей версии

### S8: Краевой случай — невалидный аргумент навигации (аналог 400)

- **GIVEN** выполняется переход на экран тренировки с аргументом deckId, не являющимся корректным UUID (например, "1" или "abc")
- **WHEN** экран тренировки загружает данные
- **THEN** экран не падает с необработанным исключением; показывается пустое или терминальное состояние («на сегодня всё»); пользователь может вернуться к списку колод

### S9: Краевой случай — несуществующая колода (аналог 404)

- **GIVEN** в БД нет колоды с UUID "X" (не создавалась либо удалена — физически или мягко)
- **WHEN** выполняется переход на экран тренировки с deckId = "X"
- **THEN** мягко удалённая и отсутствующая колода ведут себя одинаково — как отсутствующая; экран показывает пустое/терминальное состояние без краха; возврат к списку работает

**Признак локального изменения isChanged**

### S10: Создание записи выставляет isChanged = true независимо от флага

- **GIVEN** флаг синхронизации выключен (значение по умолчанию)
- **WHEN** создаётся новая запись (колода или карточка)
- **THEN** запись сохраняется с isChanged = true — признак ставится при создании всегда, независимо от состояния флага синхронизации

### S11: Изменение записи выставляет isChanged = true

- **GIVEN** в БД есть карточка с isChanged = false (значение установлено напрямую в тесте)
- **WHEN** через repository изменяются данные карточки (редактирование)
- **THEN** карточка сохраняется с isChanged = true

### S12: Признак isChanged переживает перезапуск и ничем не снимается

- **GIVEN** в БД есть записи с isChanged = true
- **WHEN** пользователь закрывает приложение, запускает его снова и выполняет любые локальные операции (просмотр, тренировка, навигация)
- **THEN** признак isChanged у записей сохраняется и не снимается — в этой фиче нет операции очистки признака (снимать его будет только будущая синхронизация)

**Счётчик правок revision**

### S13: revision увеличивается на 1 при каждом изменении

- **GIVEN** в БД есть карточка с revision = 3
- **WHEN** выполняется изменение карточки, затем ещё одно изменение
- **THEN** после первого изменения revision = 4, после второго — 5; каждое изменение записи увеличивает счётчик ровно на 1; новая запись создаётся с revision = 1

**Флаг синхронизации (DataStore)**

### S14: Флаг синхронизации по умолчанию выключен

- **GIVEN** чистая установка приложения, DataStore не содержит сохранённого значения флага
- **WHEN** приложение читает флаг синхронизации
- **THEN** возвращается false; режим удаления — физический (поведение текущей версии)

### S15: Значение флага персистентно, UI для переключения отсутствует

- **GIVEN** флаг синхронизации установлен в true напрямую в DataStore (переключателя в UI нет — флагом будет управлять будущий экран настроек сервера)
- **WHEN** приложение перезапускается
- **THEN** флаг читается как true (значение переживает перезапуск); ни на одном экране этой фичи нет элементов управления флагом; режим удаления — мягкий

### S16: Краевой случай — ошибка чтения DataStore (аналог 500)

- **GIVEN** чтение флага из DataStore завершается ошибкой (хранилище повреждено или недоступно)
- **WHEN** выполняется удаление записи
- **THEN** удаление выполняется в дефолтном режиме — физическом (флаг трактуется как выключенный); приложение не падает

**Удаление при выключенном флаге — физическое**

### S17: Физическое удаление карточки

- **GIVEN** флаг синхронизации выключен; в БД есть колода и карточка "C" (UUID) в ней
- **WHEN** выполняется удаление карточки "C"
- **THEN** строка карточки немедленно физически удаляется из БД; прямой запрос DAO по UUID "C" не находит запись; счётчик карточек колоды уменьшается

### S18: Физическое удаление колоды каскадно удаляет карточки

- **GIVEN** флаг выключен; в БД есть колода "D" с 5 карточками
- **WHEN** выполняется удаление колоды "D"
- **THEN** из БД физически удаляются строка колоды "D" и все 5 её карточек (каскад); колода исчезает из списка колод; прямые запросы по UUID колоды и её карточек не находят записи

**Удаление при включённом флаге — мягкое**

### S19: Мягкое удаление карточки

- **GIVEN** флаг включён; в БД есть карточка с isDeleted = false, isChanged = true, revision = 2
- **WHEN** выполняется удаление карточки
- **THEN** строка остаётся в БД и получает isDeleted = true, isChanged = true, revision = 3; карточка больше не возвращается ни одним запросом для UI; данные карточки сохранены до будущей отправки на сервер

### S20: Мягкое удаление колоды каскадно помечает карточки

- **GIVEN** флаг включён; в БД есть колода "D" с 4 карточками, все isDeleted = false
- **WHEN** выполняется удаление колоды "D"
- **THEN** колода остаётся в БД с isDeleted = true, isChanged = true, revision +1; каждая из 4 карточек остаётся в БД с isDeleted = true, isChanged = true, revision +1; все 5 строк физически присутствуют в БД; колода исчезает из списка колод

### S21: Мягко удалённые записи скрыты со всех экранов, счётчиков и экспорта

- **GIVEN** флаг включён; колода "A" содержит 5 карточек, из них 2 мягко удалены (isDeleted = true)
- **WHEN** пользователь открывает список колод, а также выполняется любой агрегирующий запрос (счётчики, экспорт)
- **THEN** колода "A" отображается со счётчиком 3; мягко удалённые записи не отображаются ни на одном экране и не участвуют в счётчиках и экспорте

### S22: Мягко удалённые карточки не участвуют в тренировке

- **GIVEN** флаг включён; в колоде 6 карточек, 1 мягко удалена; среди оставшихся есть карточки для показа
- **WHEN** пользователь запускает тренировку колоды и проходит сессию до конца
- **THEN** сессия состоит из 5 карточек; мягко удалённая карточка не показывается ни на одном шаге сессии

### S23: Мягко удалённая запись доступна по прямому запросу к DAO

- **GIVEN** флаг включён; карточка "C" мягко удалена (isDeleted = true)
- **WHEN** выполняется прямой запрос к DAO по UUID "C" без фильтра isDeleted
- **THEN** запись найдена в БД с исходными данными и isDeleted = true — мягко удалённые записи физически присутствуют в базе до будущей синхронизации

### S24: Переключение флага не трогает мягко удалённые записи

- **GIVEN** флаг включён; колода "D" и её карточки мягко удалены (isDeleted = true)
- **WHEN** флаг переключается на выключенный (напрямую в DataStore) и приложение перезапускается
- **THEN** мягко удалённые записи остаются в БД с isDeleted = true — не восстанавливаются на экранах и не удаляются физически; их очистка/восстановление — предмет будущей фичи синхронизации

**Рантайм-краевые случаи**

### S25: Удаление колоды во время открытой тренировки (аналог 404 в рантайме)

- **GIVEN** пользователь находится в тренировке колоды "D"; флаг синхронизации включён
- **WHEN** колода "D" (или её оставшиеся карточки) мягко удаляется, пока сессия открыта
- **THEN** экран через Flow получает обновление и корректно завершает сессию терминальным состоянием («на сегодня всё» или выход к списку), без краха и зависания

### S26: Ошибка БД при загрузке списка колод (аналог 500)

- **GIVEN** запрос к Room завершается ошибкой (повреждение БД / сбой диска)
- **WHEN** пользователь открывает экран списка колод
- **THEN** экран переходит в состояние ошибки (аналогично текущей обработке ошибок БД в `offline.storage`); приложение не падает; пользователь может повторить попытку

## OpenAPI Delta

Изменение `prepare-sync-data-model` затрагивает только локальный слой данных Android-приложения (Room, DataStore). Сетевого взаимодействия, эндпоинтов и контрактов в этой фече не появляется — дельта пуста. REST-контракт синхронизации будет определён в change на capability `sync.background`.

```yaml
# openapi-delta
# Без изменений: офлайн-подготовка данных, HTTP-слоя не касается
paths: {}
components:
  schemas: {}
```
