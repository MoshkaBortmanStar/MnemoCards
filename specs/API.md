# Контракт синхронизации MnemoCards — API v1

> **Версия контракта:** 1.0.0 (2026-09-18)
> **Статус:** действующий. Этот документ — источник истины для обеих сторон: сервера (этот репозиторий) и Android-клиента (отдельный репозиторий). Код, расходящийся с контрактом, считается багом кода.
> **Связь:** дополняет `specs/MAIN.md`. В вопросах API приоритет у этого файла.

Документ определяет модель данных, модель синхронизации, эндпоинты, коды ошибок и требования к транспорту сервера синхронизации MnemoCards. Все примеры используют реалистичные данные.

---

## 1. Версия контракта и правила его изменения

Контракт версионируется по схеме MAJOR.MINOR.PATCH. Префикс URL `/api/v1/` меняется только при смене MAJOR.

| Тип изменения | Уровень | Совместимость |
|---|---|---|
| Исправление опечатки, уточнение формулировки без смены поведения | PATCH | Полная |
| Новое опциональное поле в ответе, новый код ошибки, новый эндпоинт, ослабление ограничения | MINOR | Обратная совместимость сохраняется |
| Удаление или переименование поля, смена типа, смена семантики, новое обязательное поле запроса, изменение правил разрешения конфликтов | MAJOR | Требуется `/api/v2/` и период параллельной работы версий |

Обязательные правила совместимости:

- Обе стороны **обязаны игнорировать** неизвестные поля в полученном JSON и неизвестные коды ошибок. Это позволяет наращивать контракт без ломки второй стороны.
- Убирать поля из ответов нельзя (клиент может уже полагаться на них) — только через MAJOR.
- Контракт один на обе стороны: любое изменение этого файла сначала фиксируется здесь, потом реализуется в коде. Правка кода «мимо контракта» запрещена.

## 2. Модель данных

### 2.1. Общие типы и соглашения

| Тип | JSON-представление | Описание |
|---|---|---|
| UUID | string | Каноническая форма в нижнем регистре: `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`. Генерирует **клиент** при создании записи. Автоинкрементные числовые id не используются: они коллизируют между устройствами |
| Время | number | Целое, миллисекунды от эпохи, UTC. ISO-строки не используются нигде |
| Ревизия | number | Целое неотрицательное, см. раздел 3.2 |

Формат обмена — JSON в UTF-8 (без BOM). Имена полей — camelCase. Все поля обязательны, если явно не указано, что они nullable. Null передаётся явно. Числа — без кавычек, булевы значения — настоящие `true`/`false`.

### 2.2. Колода

**Хранимая запись** (присутствует в ответах сервера):

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `uuid` | UUID | нет | Идентификатор, назначен клиентом при создании |
| `name` | string, 1–200 символов | нет | Название колоды |
| `updatedAt` | Время | нет | Момент последней правки. Проставляет **сервер** при приёме запроса |
| `deletedAt` | Время | **да** | Не null — запись удалена (надгробие). См. 3.5 |

**Форма изменения** (присутствует в запросах клиента):

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `uuid` | UUID | нет | |
| `name` | string, 1–200 символов | нет | Содержимое обязательно всегда, в том числе при `deleted: true` — клиент удаляет существующую запись и её содержимое у него есть |
| `deleted` | boolean | нет | `true` — удалить запись на сервере |

### 2.3. Карточка

**Хранимая запись** (в ответах):

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `uuid` | UUID | нет | Идентификатор, назначен клиентом при создании |
| `deckUuid` | UUID | нет | Колода, которой принадлежит карточка. Неизменна: перенос карточки между колодами контрактом не поддерживается |
| `front` | string, 1–10000 символов | нет | Лицевая сторона (слово) |
| `back` | string, 1–10000 символов | нет | Обратная сторона (перевод) |
| `easeFactor` | number (double), [1.3, 5.0] | нет | Коэффициент лёгкости (модель SM-2; новая карточка — 2.5) |
| `repetition` | number (int), ≥ 0 | нет | Номер повторения: число успешных подряд повторений |
| `intervalDays` | number (int), [0, 36500] | нет | Длина текущего интервала повторения, дней; 0 — карточка новая или к показу готова |
| `dueAt` | Время | нет | Дата следующего показа |
| `updatedAt` | Время | нет | Проставляет сервер |
| `deletedAt` | Время | **да** | Не null — надгробие |

**Форма изменения** (в запросах): те же поля, что у хранимой записи, кроме `updatedAt` и `deletedAt`, плюс:

| Поле | Тип | Описание |
|---|---|---|
| `deleted` | boolean | `true` — удалить на сервере |

Правила:

- Параметры интервальных повторений (`easeFactor`, `repetition`, `intervalDays`, `dueAt`) **обязательны в каждом изменении**. Без них занятия на одном устройстве не переносились бы на другие.
- Изменение — всегда **полная запись**, а не патч отдельных полей. Сервер хранит только последнюю версию и не хранит историю правок.
- Время правки клиент **не хранит и не присылает** — `updatedAt` и `deletedAt` проставляет только сервер.

## 3. Модель синхронизации

### 3.1. Общий принцип

Синхронизация — обмен дельтами в одном запросе: клиент отправляет свои локальные изменения и получает изменения, случившиеся на сервере после указанной ревизии. Отдельного запроса «скачать всё» нет: первая синхронизация — это `since = 0`.

Ответ сервера содержит **все** записи потока, изменённые после `since`, **включая только что принятые из этого же запроса**. Клиент применяет ответ как каноническое состояние (узнаёт проставленные сервером `updatedAt`/`deletedAt`), не различая «своё» и «чужое».

### 3.2. Ревизии

Что передавать, определяет **монотонный счётчик ревизий на сервере**, а не время. Часы не участвуют в отборе изменений.

- Счётчик — целое, на **учётную запись**, начинается с 1, увеличивается на 1 за каждую принятую правку (создание, изменение, удаление — любое), никогда не сбрасывается и не пропускает значения.
- Каждая принятая правка получает уникальный номер ревизии и сохраняется в изменённой строке.
- **Потоки синхронизации** — независимые: список колод и карточки каждой колоды. Ревизия потока — значение общего счётчика аккаунта в момент последнего изменения этого потока. Правка карточки не двигает ревизию списка колод; переименование колоды не двигает ревизию карточек этой колоды.
- Клиент хранит последнее полученное значение ревизии **на каждый поток**: одну для списка колод и по одной на каждую колоду для её карточек. Присылает его в поле `since`.
- Сервер возвращает записи потока с ревизией больше `since` и новое значение `revision` — его клиент обязан сохранить как новый `since`.

Дополнительные инварианты сервера:

- Изменения одного запроса применяются в порядке массива; каждая правка получает следующий номер. Повторяющийся `uuid` внутри одного массива допустим — побеждает последняя позиция (тот же принцип last-write-wins).
- Всем правкам одного запроса присваивается **одно** значение `updatedAt` — момент приёма запроса сервером.
- Запрос атомарен: любая ошибка валидации (400/413) — не применено ничего, счётчик ревизий не двигается.
- Ответ собирается по возрастанию ревизии.

### 3.3. Dirty-флаг и алгоритм клиента

Dirty — локальный (клиентский) флаг «запись изменена и ещё не доставлена на сервер». Локально изменённые записи клиент помечает dirty и отправляет **только их**; после успешной синхронизации флаг снимается.

Алгоритм клиента для одного потока:

1. Снять снапшот dirty-записей (включая локально удалённые — они уходят с `deleted: true`).
2. `POST` с `since` = хранимая ревизия потока и `changes` = снапшот. Если dirty-записей больше лимита (см. 413) — отправлять чанками не более 1000, по мере успеха.
3. При ответе 200:
   - применить каждую запись ответа: перезаписать локальную копию; запись с `deletedAt != null` — удалить локально совсем;
   - записи ответа, которых **не было** в отправке и у которых локальная копия dirty (изменена после снапшота, пока запрос летел), не применять — локальная правка останется dirty и уйдёт следующей синхронизацией, сервер разрешит коллизию по last-write-wins;
   - сохранить `revision` как новый `since` потока;
   - снять dirty у отправленных записей, **не изменявшихся после снятия снапшота** (для этого клиент ведёт локальный счётчик правок на запись и сравнивает его при снятии флага).
4. При любом не-2xx dirty не снимается — изменения уйдёт повторной попыткой.

Полная сессия синхронизации: **сначала список колод, потом карточки каждой известной живой колоды**. Для колоды, впервые увиденной в ответе списка, карточки запрашиваются с `since = 0`. Частота и триггеры сессии (открытие приложения, кнопка, фон) — политика клиента, контрактом не регулируются.

### 3.4. Конфликты: last-write-wins

**Побеждает запись, поступившая на сервер позже.** Сервер не сравнивает содержимое и не мерджит поля: каждая принятая правка целиком перезаписывает хранимую строку.

Следствие, принимаемое осознанно: правка, **сделанная раньше, но доставленная позже**, полностью перезапишет более свежую. Пример: телефон правит карточку утром без сети; вечером планшет правит ту же карточку и синхронизируется первым — вечером телефон выходит в сеть, его утренняя правка приходит на сервер позже и **вытесняет** правку планшета целиком.

Обоснование: сервером пользуется один человек, работающий на устройствах последовательно, а не параллельно. Одновременные офлайн-правки одной записи — редкое событие; цена построчного мерджа и истории версий для этого сценария не оправдана. Проигравшая правка при желании восстанавливается повторным вводом.

Это же правило разрешает коллизии удаления: удаление — обычная правка, поступившая позже — побеждает; наоборот, более поздняя правка содержимого «оживляет» удалённую запись (`deletedAt` сбрасывается в null).

### 3.5. Удаление и надгробия

Удаление **мягкое**: запись помечается `deletedAt`, физически не стирается сразу. Иначе другое устройство никогда не узнает об удалении и вернёт запись при следующей синхронизации.

- Клиент помечает запись dirty + `deleted: true` и отправляет в общем порядке. Сервер проставляет `deletedAt` своим временем.
- Получив из ответа запись с `deletedAt != null`, клиент обязан удалить её локально целиком.
- **Каскад колоды:** удаление колоды помечает удалёнными и все её карточки. Применив надгробие колоды, клиент обязан удалить локально все её карточки. Обратного каскада нет: восстановление («оживление») колоды более поздней правкой не восстанавливает карточки.
- **Срок хранения надгробий — 180 дней** с момента удаления (конфигурируется на сервере; увеличение безопасно всегда). По истечении срока фоновая чистка физически стирает надгробия вместе с данными; чистка надгробия колоды стирает и надгробия её карточек.

**Защита от «зомби».** После физической чистки клиент с давно не синхронизированным `since` мог бы не увидеть надгробие и воскресить запись. Поэтому сервер хранит **отметку полноты** — минимальную ревизию, с которой ещё гарантированно доступны все изменения, включая неудалённые надгробия. Если запрос пришёл с `since` ниже этой отметки — дельта невозможна; то же правило применяется, если `since` больше текущего счётчика (признак потери/отката данных сервера, например после восстановления БД с носителя). В обоих случаях сервер отвечает полным срезом потока:

```json
{ "revision": 131, "fullSync": true, "decks": [ "…все живые записи и удержанные надгробия…" ] }
```

При `fullSync: true` клиент обязан **полностью заменить** локальное состояние потока содержимым ответа: применить все записи ответа и удалить локальные записи потока, которых в ответе нет. Отправленные в этом же запросе изменения применяются сервером до формирования среза и попадают в ответ.

### 3.6. Идемпотентность

Повторная отправка того же запроса безопасна: записи идентифицируются UUID, повторное применение той же правки по last-write-wins не задваивает данные (счётчик ревизий при этом двигается — это допустимо). Клиент может ретраить запрос после любой сетевой ошибки без риска.

## 4. Аутентификация

Авторизация — по логину и паролю, обмен на пару токенов. Регистрации **нет**: учётные записи заводятся вручную прямо в базе сервера; эндпоинт создания учётных записей отсутствует и в v1 не планируется.

**Токены:**

- `accessToken` — срок жизни **15 минут** по умолчанию.
- `refreshToken` — срок жизни **30 дней** по умолчанию.
- Значения по умолчанию конфигурируются на сервере; клиент сроков не предполагает и читает поля `accessTokenExpiresAt` / `refreshTokenExpiresAt` из ответа.
- `refreshToken` **одноразовый** (ротация): каждый успешный refresh выдаёт новую пару и гасит использованный refresh. Потеря ответа refresh (сеть оборвалась после обработки) означает разовый выход в экран входа — для одного пользователя это приемлемо.

**Использование:** все `/sync/*`-эндпоинты требуют заголовок

```
Authorization: Bearer <accessToken>
```

`login`, `refresh` и `health` работают без него.

**Поведение клиента при 401 на синхронизации:** один раз выполнить refresh, повторить исходный запрос; если refresh не удался — стереть токены и показать экран входа. Хранение пароля для автологина — политика клиента, не контрактуется.

**Требования к серверу (фиксируются для реализации):**

- Пароли хранятся **только** хешем — bcrypt (cost ≥ 12) или argon2id. Откртый вид недопустим нигде, включая логи.
- Токены — 256-битные случайные значения; в базе хранится их хеш (например, SHA-256) и срок; refresh дополнительно помечается использованным.
- Токены передаются только по HTTPS (см. раздел 7) и привязаны к учётной записи; данные и ревизии разных учётных записей изолированы.

## 5. Эндпоинты

Базовый префикс: `/api/v1`. Content-Type запросов и ответов — `application/json; charset=utf-8`.

### 5.1. POST /api/v1/auth/login

Обмен логина и пароля на пару токенов. Авторизация не нужна.

Запрос:

| Поле | Тип | Ограничение |
|---|---|---|
| `username` | string | 1–100 символов |
| `password` | string | 1–256 символов |

```json
{
  "username": "mikhail",
  "password": "verein-durch-die-wand"
}
```

Ответ 200:

| Поле | Тип | Описание |
|---|---|---|
| `accessToken` | string | Токен доступа |
| `accessTokenExpiresAt` | Время | Момент истечения access |
| `refreshToken` | string | Одноразовый токен обновления |
| `refreshTokenExpiresAt` | Время | Момент истечения refresh |

```json
{
  "accessToken": "a3f81c6e0b2d49f7a8c5e1d03b6f9a24c7e85d10f3a6b29c4d07e18f5b3ac269",
  "accessTokenExpiresAt": 1789713300000,
  "refreshToken": "6d2c9f41e08a5b37c6d19f24a8e0b5c37f91d6048a2e5c7b1f93d08a64b2e75c",
  "refreshTokenExpiresAt": 1792304400000
}
```

Ошибки: `401 INVALID_CREDENTIALS` — неверный логин или пароль; `400 VALIDATION_FAILED`.

### 5.2. POST /api/v1/auth/refresh

Обновление пары токенов. Авторизация не нужна.

Запрос:

| Поле | Тип | Описание |
|---|---|---|
| `refreshToken` | string | Ранее выданный refresh-токен |

```json
{
  "refreshToken": "6d2c9f41e08a5b37c6d19f24a8e0b5c37f91d6048a2e5c7b1f93d08a64b2e75c"
}
```

Ответ 200 — тот же формат, что у login: новая пара токенов; использованный refresh гасится и повторно неприменим.

Ошибки: `401 REFRESH_INVALID` — токен неизвестен, истёк или уже использован. Клиент обязан стереть токены и перевести пользователя на экран входа.

### 5.3. POST /api/v1/sync/decks

Синхронизация списка колод: создание, переименование, удаление. Требует Bearer-токен.

Запрос:

| Поле | Тип | Ограничение | Описание |
|---|---|---|---|
| `since` | number (int) | ≥ 0 | Хранимая клиентом ревизия потока «список колод»; 0 при первой синхронизации |
| `changes` | массив форм изменения колоды | 0–1000 записей | Локальные dirty-изменения; может быть пустым (опрос чужих изменений) |

```json
{
  "since": 128,
  "changes": [
    {
      "uuid": "3f9a2c7e-1b4d-4e8f-9a2c-7e5b1d4f8a30",
      "name": "Немецкий A1 · сентябрь",
      "deleted": false
    },
    {
      "uuid": "77c9e0b2-a5d3-4f18-b6c2-09e14d7a3b51",
      "name": "Испанский — глаголы",
      "deleted": false
    },
    {
      "uuid": "5a3d90c1-2f8b-4c6e-8d0a-91f7b2e4c58a",
      "name": "Французский",
      "deleted": true
    }
  ]
}
```

(Первое — переименование существующей колоды, второе — создание новой, третье — удаление.)

Ответ 200:

| Поле | Тип | Описание |
|---|---|---|
| `revision` | number (int) | Новая ревизия потока; клиент сохраняет как `since` |
| `fullSync` | boolean | `true` — полный срез, клиент заменяет состояние потока целиком (см. 3.5) |
| `decks` | массив записей колоды | Все изменённые после `since` записи, включая принятые из этого запроса |

```json
{
  "revision": 131,
  "fullSync": false,
```

### 5.5. GET /api/v1/health

Проверка доступности без авторизации — для кнопки «Проверить соединение» в настройках приложения.

Ответ 200:

```json
{ "status": "ok" }
```

Ответ 503 — приложение живо, но база недоступна:

```json
{ "status": "degraded" }
```

Сервер проверяет БД тривиальным запросом перед ответом. Клиент трактует любой 2xx как «соединение есть», 503 — «сервер доступен, но неисправен», сетевую ошибку — «сервер недоступен».

## 6. Коды ошибок и поведение клиента

Формат тела ошибки (кроме `health`, см. 5.5):

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "easeFactor: expected between 1.3 and 5.0, got 0.8"
  }
}
```

`message` — человекочитаемое пояснение для логов и отладки, на него нельзя завязываться программно. Контрактует поведение только `code` + HTTP-статус.

| HTTP | Код | Когда | Действие клиента |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | Битый JSON, нарушение типов/ограничений полей, `deckUuid` не совпадает с путём | **Не ретраить.** Записать в лог, показать пользователю общую ошибку. Это ошибка программирования одной из сторон |
| 401 | `INVALID_CREDENTIALS` | `login`: неверный логин или пароль | Показать ошибку формы входа |
| 401 | `TOKEN_INVALID` | `/sync/*`: токен отсутствует, неизвестен или истёк | Один refresh → повтор исходного запроса; не вышло — стереть токены, экран входа |
| 401 | `REFRESH_INVALID` | `refresh`: токен неизвестен, истёк или уже использован | Стереть токены, экран входа |
| 404 | `DECK_NOT_FOUND` | `cards`: колода не существует / удалена / вычищена | Удалить локальные карточки колоды и её `since`; продолжить сессию |
| 413 | `TOO_MANY_CHANGES` | Больше 1000 записей в `changes`; nginx может отдать 413 и без JSON-тела при превышении размера тела | Уменьшить чанк (вдвое), отправить снова |
| 500 | `INTERNAL_ERROR` | Неисправность сервера | Повторить позже с нарастающим ожиданием |
| 503 | — | `health`: БД недоступна | См. 5.5 |

Общие правила повторов: сетевые ошибки и 5xx ретраятся с экспоненциальной задержкой (например, 1 мин → 5 мин → 30 мин, далее — при следующей сессии); запрос идемпотентен (3.6), повтор безопасен. 400 не ретраится никогда.

## 7. Транспорт и развёртывание

Приложение работает на Raspberry Pi за обратным прокси nginx. Требования к развёртыванию:

1. Приложение слушает **только** обычный HTTP на `127.0.0.1:8080`. Прослушивание внешних интерфейсов запрещено: TLS и внешний мир — забота nginx.
2. nginx — единственная точка входа: HTTPS (443) с проксированием на `127.0.0.1:8080`, заголовки `X-Forwarded-Proto`/`X-Forwarded-For`.
3. Сертификат — от доверенного CA (например, Let's Encrypt). Self-signed допустим только если клиент настроен на пиннинг этого сертификата; клиент не обязан принимать непроверенные сертификаты.
4. TLS ≥ 1.2, рекомендовано 1.3.
5. `client_max_body_size` ≥ 16 MB и `proxy_read_timeout` ≥ 60 s — синхронизационные запросы с чанком до 1000 карточек доходят до нескольких мегабайт.
6. Включить сжатие gzip для `application/json` — основной трафик это JSON.
7. Ограничить частоту запросов на `/api/v1/auth/login` (`limit_req`) — единственный эндпоинт, принимающий пароль из интернета.
8. На сервере включён NTP: `updatedAt` не влияет на корректность синхронизации (порядок определяют ревизии), но кривые метки времени мешают отладке.
9. Клиент в продакшене обращается только по `https://`. Обращение по голому HTTP допустимо лишь в девелопменте (эмулятор → машина разработчика).

## 8. Известные ограничения

1. **Last-write-wins без мерджа.** Правка, сделанная раньше, но доставленная позже, полностью перезаписывает более свежую. Осознанное решение для одного пользователя с последовательной работой на устройствах (3.4). История правок не хранится.
2. **Нет построчного мерджа и конфликтных диалогов** — проигравшая правка не сохраняется нигде.
3. **Перенос карточки между колодами не поддерживается.** Обходной путь — удалить и создать заново (новый UUID, статистика повторений теряется).
4. **Восстановление удалённой колоды не восстанавливает карточки** (каскадное надгробие, 3.5). Undelete как функция не гарантируется: после применения надгробия клиент отбрасывает запись.
5. **Нет пагинации ответов** — дельта отдаётся целиком. Масштаб персональный (тысячи карточек); при экстремально длинной истории первой синхронизации объём ограничен чанками запроса, но не ответа.
6. **Ротация refresh-токенов**: потеря ответа refresh (разрыв сети после обработки) приводит к разовому выходу в экран входа.
7. **Регистрации нет** — учётные записи создаются вручную INSERT-запросом в базу сервера; API управления пользователями отсутствует.
8. **Часы сервера не влияют на корректность**, но искажают `updatedAt`/`deletedAt` в отладке (см. 7, п. 8).
