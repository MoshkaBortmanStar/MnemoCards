# BDD Spec: Управление карточками внутри колоды

> **Change ID:** `add-card-management`
> **Дата:** 2026-09-17

Сводка: спецификация покрывает новую capability `cards.management` — экран содержимого колоды со списком карточек и порядком «новые сверху» (S1–S3), добавление карточек через форму с валидацией (S4–S10), редактирование по тапу (S11–S14), удаление с подтверждением (S15–S18), персистентность правок в Room (S19), автоматическое обновление счётчика карточек (S20–S21) и интеграцию с тренировкой (S22–S23). Фича полностью офлайн: сети и HTTP нет, поэтому ошибки описаны как аналоги HTTP-кодов: валидация пустых полей — 400-аналог (S6–S8), устаревшие идентификаторы — 404-аналог (S24–S25), ошибка Room — 500-аналог (S26).

## Сценарии

### S1: Открытие экрана содержимого колоды

- **GIVEN** приложение запущено; в Room есть колода «Английский базовый» (id=1) с тремя карточками, включая «hello / привет»
- **WHEN** на экране списка колод пользователь выполняет тап по элементу колоды «Английский базовый»
- **THEN** открывается экран содержимого колоды: в заголовке — название колоды, в списке 3 элемента, каждый показывает лицевую и обратную сторону («hello — привет» и т.д.); видна кнопка добавления карточки; доступен возврат к списку колод

### S2: Краевой случай — пустая колода

- **GIVEN** в Room есть колода (id=1), не содержащая ни одной карточки
- **WHEN** пользователь открывает экран содержимого этой колоды
- **THEN** список пуст; показано пустое состояние с сообщением вида «В колоде пока нет карточек»; кнопка добавления карточки доступна; приложение не падает

### S3: Порядок карточек — новые сверху

- **GIVEN** в колоде несколько карточек, добавленных в разное время
- **WHEN** пользователь открывает экран содержимого колоды
- **THEN** карточки отсортированы по времени добавления по убыванию: самая новая — вверху списка; при добавлении новой карточки она появляется первой без перезагрузки экрана

### S4: Открытие формы добавления карточки

- **GIVEN** открыт экран содержимого колоды
- **WHEN** пользователь выполняет тап по кнопке добавления карточки
- **THEN** открывается форма карточки с двумя пустыми полями («Лицевая сторона», «Перевод») и кнопкой «Сохранить»

### S5: Успешное добавление карточки

- **GIVEN** открыта форма добавления, оба поля пусты
- **WHEN** пользователь вводит «cat» в поле лицевой стороны и «кошка» в поле перевода, нажимает «Сохранить»
- **THEN** форма закрывается; карточка «cat / кошка» появляется в списке содержимого колоды без перезагрузки экрана (первой строкой, согласно S3); в Room создана запись CardEntity с deckId этой колоды

### S6: Краевой случай — пустое обязательное поле (400-аналог)

- **GIVEN** открыта форма добавления карточки
- **WHEN** одно из обязательных полей оставлено пустым — лицевая сторона (при заполненном переводе «собака») или перевод (при заполненной лицевой стороне «dog»), — нажата «Сохранить»
- **THEN** сохранение не выполняется; у пустого поля показана ошибка валидации (текст вида «Заполните поле»); форма остаётся открытой с введёнными значениями; новых записей в Room нет

### S7: Краевой случай — оба поля пусты (400-аналог)

- **GIVEN** открыта форма добавления карточки
- **WHEN** оба поля пусты, нажата «Сохранить»
- **THEN** сохранение заблокировано: ошибки валидации у обоих полей (либо кнопка «Сохранить» неактивна при пустых полях); в Room пустая карточка не создаётся

### S8: Краевой случай — только пробельные символы (400-аналог)

- **GIVEN** открыта форма добавления карточки
- **WHEN** в оба поля введены только пробелы и переводы строк («   »), нажата «Сохранить»
- **THEN** значения после trim считаются пустыми; сохранение блокируется с ошибкой валидации; в Room карточка из одних пробелов не создаётся

### S9: Краевой случай — дубликат карточки разрешён

- **GIVEN** в колоде уже есть карточка «cat / кошка»
- **WHEN** через форму добавления сохранена ещё одна карточка с теми же значениями
- **THEN** сохранение выполняется успешно; в списке две независимые записи «cat / кошка» (валидация уникальности в фичу не входит)

### S10: Краевой случай — длинный текст

- **GIVEN** открыта форма добавления карточки
- **WHEN** пользователь сохраняет карточку с текстом 200+ символов в каждом поле
- **THEN** карточка сохраняется в Room и отображается в списке; длинный текст переносится по строкам или усекается многоточием; макет списка и кнопок не ломается

### S11: Открытие формы редактирования по тапу на карточку

- **GIVEN** на экране содержимого колоды есть карточка «cat / кошка»
- **WHEN** пользователь выполняет тап по элементу этой карточки
- **THEN** открывается та же форма с двумя полями, предзаполненными текущими значениями («cat», «кошка»); сохранение обновляет именно эту карточку, а не создаёт новую

### S12: Успешное редактирование карточки

- **GIVEN** открыта форма редактирования карточки «cat / кошка»
- **WHEN** лицевая сторона изменена «cat» → «a cat», нажата «Сохранить»
- **THEN** форма закрывается; в списке отображается «a cat / кошка», прежнее значение исчезло; количество карточек в колоде не изменилось; запись в Room обновлена

### S13: Краевой случай — очистка поля при редактировании (400-аналог)

- **GIVEN** открыта форма редактирования карточки «cat / кошка»
- **WHEN** поле перевода очищено, нажата «Сохранить»
- **THEN** сохранение блокируется с ошибкой валидации; в Room остаются прежние значения карточки («cat / кошка»)

### S14: Отмена редактирования

- **GIVEN** открыта форма редактирования, текст изменён, но не сохранён
- **WHEN** пользователь нажимает системную кнопку «Назад» без «Сохранить»
- **THEN** происходит возврат к экрану содержимого; карточка показывает прежние значения; в Room изменений нет

### S15: Диалог подтверждения удаления

- **GIVEN** на экране содержимого колоды есть карточка
- **WHEN** пользователь выполняет тап по действию удаления на элементе карточки
- **THEN** открывается диалог подтверждения с текстом вида «Удалить карточку?» и кнопками «Удалить» и «Отмена»; карточка до выбора остаётся в списке

### S16: Подтверждение удаления

- **GIVEN** открыт диалог подтверждения удаления карточки
- **WHEN** нажата «Удалить»
- **THEN** диалог закрывается; карточка исчезает из списка без перезагрузки экрана; запись удалена из Room

### S17: Отмена удаления

- **GIVEN** открыт диалог подтверждения удаления карточки
- **WHEN** нажата «Отмена»
- **THEN** диалог закрывается; карточка осталась в списке; запись в Room не тронута

### S18: Краевой случай — удаление последней карточки колоды

- **GIVEN** в колоде ровно одна карточка
- **WHEN** пользователь удаляет её с подтверждением
- **THEN** список становится пустым; показывается пустое состояние (как в S2); приложение не падает

### S19: Персистентность — любая правка карточек переживает перезапуск

- **GIVEN** в колоде выполнена операция управления карточками: добавление, редактирование или удаление
- **WHEN** процесс приложения убит, приложение перезапущено, открыт экран содержимого колоды
- **THEN** результат операции отражён в списке: добавленная и отредактированная карточки присутствуют с актуальными значениями, удалённая отсутствует и не восстанавливается (персистентность Room как единого источника данных уже доказана в change-002; здесь проверяется единое свойство для всех правок карточек)

### S20: Счётчик карточек обновляется после добавления

- **GIVEN** на экране списка колод у колоды отображается счётчик «3»
- **WHEN** пользователь добавляет карточку в эту колоду и возвращается к списку колод
- **THEN** счётчик колоды автоматически показывает «4» (обновление через Flow из Room, без ручной перезагрузки экрана)

### S21: Счётчик карточек обновляется после удаления

- **GIVEN** на экране списка колод у колоды отображается счётчик «3»
- **WHEN** пользователь удаляет одну карточку этой колоды и возвращается к списку колод
- **THEN** счётчик колоды автоматически показывает «2»

### S22: Новая карточка попадает в тренировку

- **GIVEN** в колоду добавлена новая карточка «cat / кошка»
- **WHEN** из списка колод запускается тренировка этой колоды
- **THEN** новая карточка входит в сессию повторения вместе с остальными карточками колоды (сессия читает колоду из Room)

### S23: Редактирование карточки при открытой сессии тренировки

- **GIVEN** открыта сессия тренировки колоды, текущая карточка — «cat»
- **WHEN** пользователь возвращается к экрану содержимого колоды, редактирует карточку «cat» → «a cat», сохраняет и возвращается в сессию тренировки
- **THEN** сессия показывает обновлённый текст «a cat»: данные читаются из Room через Flow, экран тренировки актуализируется без пересоздания сессии вручную

### S24: Краевой случай — устаревший идентификатор колоды (404-аналог)

- **GIVEN** навигация на экран содержимого колоды инициирована с deckId=99, которого нет в Room (битый/устаревший аргумент навигации)
- **WHEN** экран содержимого колоды пытается открыться
- **THEN** показано состояние «колода не найдена» либо автоматический возврат к списку колод; пустой список не выдаётся за успешную загрузку; приложение не падает; данные в Room не создаются

### S25: Краевой случай — устаревшая карточка в форме редактирования (404-аналог)

- **GIVEN** форма редактирования открыта для карточки id=42, запись которой уже удалена из Room
- **WHEN** пользователь нажимает «Сохранить»
- **THEN** новая карточка не создаётся (update несуществующей записи не становится insert); показано состояние «карточка не найдена» либо возврат к списку; приложение не падает

### S26: Краевой случай — ошибка Room при любой операции с карточками (500-аналог)

- **GIVEN** операция с карточками завершается исключением Room — чтение списка (повреждение БД, эмулируется в тестах), insert/update при сохранении или удаление
- **WHEN** выполняется соответствующее действие: загрузка списка, «Сохранить» в форме, подтверждение удаления в диалоге
- **THEN** приложение не падает и действует по единому правилу обработки: при ошибке чтения — состояние ошибки с сообщением и возможностью повторить (пустой список не выдаётся за успех); при ошибке записи — сообщение вида «Не удалось сохранить», форма остаётся открытой с введёнными значениями (ввод не теряется), список не изменился, карточка не удалена

## OpenAPI Delta

Изменения контракта API относительно текущего состояния проекта: фича офлайн-only, взаимодействие идёт исключительно с локальной базой Room; сетевой слой (Retrofit/OkHttp) и REST-backend не затрагиваются — эндпоинтов и схем не появляется.

```yaml
# openapi-delta
# Изменение не затрагивает сеть: HTTP-контракт в этой фиче отсутствует по определению.
paths: {}
components:
  schemas: {}
```
