# BDD Spec: Фоновая синхронизация колод с сервером

> **Change ID:** `add-background-sync`
> **Дата:** 2026-09-16

Сводка: спецификация покрывает capability `sync.background` — полный цикл фоновой сессии и порядок потоков (S1–S5), применение ответов и работу признаков локальных изменений со счётчиком правок (S6–S11), авторизацию и прозрачный refresh токена (S12–S14), ошибки сети, 400, 401, 404, 500 и невалидные ответы (S15–S19), изоляцию синхронизации от основного функционала и устойчивость UI (S20–S24). Имена операций и полей приведены по specs/openapi.yaml и specs/API.md — при расхождении приоритет у этих файлов. Нефункциональные требования (тёмная тема, границы слоёв, фиксированные пакеты, только сгенерированные сетевые модели) — обязательные конвенции кодогенерации по specs/MAIN.md, отдельными сценариями не раскладываются.

## Сценарии

### S1: Автозапуск синхронизации при открытии приложения

- **GIVEN** Пользователь вошёл, синхронизация настроена, access/refresh токены сохранены; сервер доступен; локальных изменений нет; для потока колод сохранена ревизия 42
- **WHEN** Пользователь открывает приложение (запускается MainActivity)
- **THEN** В фоне, не блокируя UI, стартует сессия: `POST /api/v1/sync/decks` с `since=42` и пустым массивом `changes`, затем `POST /api/v1/sync/decks/{deckUuid}/cards` для каждой живой колоды из ответа; ответы применяются к Room; время и статус успеха фиксируются на экране настроек

### S2: Ручной запуск с экрана настроек

- **GIVEN** Пользователь находится на экране настроек; синхронизация настроена; сессия не выполняется
- **WHEN** Нажимается кнопка «Синхронизировать сейчас»
- **THEN** Запускается фоновая сессия (последовательность как в S1); экран настроек показывает состояние «выполняется», по завершении — результат и ошибки последней синхронизации; навигация и UI остаются отзывчивыми

### S3: Порядок сессии — сначала колоды, затем карточки живых колод

- **GIVEN** `POST /api/v1/sync/decks` отвечает 200: две живые колоды (uuid=1, uuid=2) и одна колода uuid=3 с признаком удаления
- **WHEN** Клиент применяет ответ списка колод и продолжает сессию
- **THEN** Запросы `POST /api/v1/sync/decks/{deckUuid}/cards` выполняются только для колод 1 и 2, каждая со своей сохранённой ревизией; колода 3 удаляется из локальной БД полностью, её карточки не запрашиваются

### S4: Краевой случай — новая колода запрашивается с нулевой ревизии

- **GIVEN** В ответе списка колод присутствует колода id=9, ранее не встречавшаяся; локальная ревизия для её потока карточек отсутствует
- **WHEN** Клиент запрашивает карточки колоды 9
- **THEN** Запрос `POST /api/v1/sync/decks/9/cards` (deckUuid колоды 9) отправляется с `since=0`; все полученные карточки применяются к Room; ревизия из ответа сохраняется как локальная ревизия потока колоды 9

### S5: Отправка только локально изменённых записей, включая удалённые

- **GIVEN** В Room в одной колоде: колода A и карточки x1, x2, x3; A и x1 помечены локально изменёнными, x2 — нет, x3 локально удалена (tombstone) и помечена
- **WHEN** Выполняется запрос синхронизации потока этой колоды
- **THEN** Тело запроса содержит A, x1 и x3 (с признаком удаления) и не содержит x2; счётчики правок отправленных записей фиксируются клиентом в момент отправки

### S6: Применение ответа — перезапись локальных записей серверными

- **GIVEN** Сервер отвечает 200 с изменёнными записями: колода переименована, у карточки обновлён перевод
- **WHEN** Клиент применяет успешный ответ
- **THEN** Локальные записи перезаписываются серверными значениями; список колод и данные сессии обновляются автоматически через Flow из Room; ревизия потока принимает значение из ответа

### S7: Краевой случай — запись, удалённая на сервере, удаляется локально полностью

- **GIVEN** Сервер отвечает 200; среди записей ответа карточка x5 с признаком удаления
- **WHEN** Клиент применяет ответ
- **THEN** Карточка x5 физически удаляется из Room (tombstone не создаётся); она исчезает из счётчиков колоды и не попадает в сессии повторения; ревизия потока обновляется

### S8: Краевой случай — полный срез заменяет состояние потока

- **GIVEN** Сервер отвечает 200 с признаком `fullSync=true` и полным набором записей потока
- **WHEN** Клиент применяет ответ
- **THEN** Локальное состояние потока полностью заменяется содержимым ответа: записи ответа перезаписываются, локальные записи потока, отсутствующие в ответе, удаляются полностью; ревизия сохраняется из ответа

### S9: Снятие признака локального изменения после успешного ответа

- **GIVEN** Записи A и x1 отправлены, их счётчики правок зафиксированы при отправке (A=3, x1=7) и с тех пор не менялись; получен ответ 200
- **WHEN** Клиент применяет ответ
- **THEN** Признак локального изменения снимается с A и x1 (текущие счётчики совпали с зафиксированными); записи исключаются из отправки следующих сессий

### S10: Краевой случай — запись изменена, пока запрос был в пути

- **GIVEN** Карточка x1 отправлена со счётчиком правок 7; пока запрос был в пути, пользователь отредактировал x1 (счётчик стал 8); получен ответ 200
- **WHEN** Клиент применяет ответ
- **THEN** Признак локального изменения с x1 не снимается (8 ≠ 7); правка пользователя сохраняется; x1 войдёт в отправку следующей сессии

### S11: Подтверждение локального удаления сервером

- **GIVEN** Локально удалённая карточка x3 (tombstone) отправлена на сервер; получен ответ 200; счётчик правок x3 не менялся
- **WHEN** Клиент применяет ответ
- **THEN** Tombstone x3 удаляется из Room полностью; признак локального изменения снимается; карточка не появляется в данных колоды

### S12: Краевой случай — 401: прозрачный refresh и повтор запроса

- **GIVEN** Access-токен истёк; refresh-токен валиден; выполняется запрос `POST /api/v1/sync/decks`
- **WHEN** Сервер отвечает 401
- **THEN** Клиент вызывает `POST /api/v1/auth/refresh`, сохраняет новую пару токенов и повторяет исходный `POST /api/v1/sync/decks` с новым access-токеном; сессия продолжается штатно; для пользователя процесс прозрачен

### S13: Краевой случай — refresh-токен отклонён: состояние «требуется вход»

- **GIVEN** Access-токен истёк; `POST /api/v1/auth/refresh` отвечает 401 (refresh-токен отклонён)
- **WHEN** Клиент получает отказ refresh
- **THEN** Состояние синхронизации меняется на «требуется вход»; сессия останавливается; локальные данные, ревизии и признаки изменений сохраняются без потерь; на экране настроек отображается «требуется вход»; локальный функционал полностью работоспособен

### S14: Краевой случай — синхронизация не настроена

- **GIVEN** Пользователь не выполнял вход; синхронизация не настроена
- **WHEN** Пользователь открывает приложение и пользуется им
- **THEN** Автозапуск синхронизации и сетевые запросы не выполняются; на экране настроек — приглашение войти вместо статуса; колоды, тренировка, создание и редактирование карточек работают в полном объёме

### S15: Краевой случай — сеть недоступна

- **GIVEN** Синхронизация настроена; устройство в авиарежиме, соединение не устанавливается
- **WHEN** Сессия запускается автоматически или кнопкой на настройках
- **THEN** Сетевой вызов завершается ошибкой соединения без HTTP-ответа; сессия прекращается с ошибкой; время и ошибка фиксируются на настройках; локальные данные, ревизии и признаки не изменяются; приложение работает без ограничений

### S16: Краевой случай — HTTP 500 от сервера

- **GIVEN** `POST /api/v1/sync/decks` выполнен успешно; при запросе `POST /api/v1/sync/decks/5/cards` (deckUuid колоды 5) сервер отвечает 500
- **WHEN** Клиент получает 500
- **THEN** Сессия прерывается ошибкой сервера; результаты уже завершённых потоков остаются применёнными; ревизия потока колоды 5 не меняется; ошибка 500 отображается на настройках; локальный функционал не затронут

### S17: Краевой случай — HTTP 400: серверная валидация отклонила запись

- **GIVEN** Среди отправленных записей есть запись, не проходящая серверную валидацию; `POST /api/v1/sync/decks` отвечает 400 с описанием ошибки по контракту
- **WHEN** Клиент получает 400
- **THEN** Тело ответа не применяется; признак локального изменения не снимается ни с одной записи потока (успешного ответа не было); ревизия не обновляется; ошибка с описанием выводится на настройках; остальной функционал работает

### S18: Краевой случай — HTTP 404 на поток карточек

- **GIVEN** Список колод синхронизирован успешно; к моменту запроса карточек колода id=5 удалена на сервере — `POST /api/v1/sync/decks/5/cards` (deckUuid колоды 5) отвечает 404
- **WHEN** Клиент получает 404
- **THEN** Поток трактуется как удалённый на сервере по правилам specs/API.md: колода 5 и её карточки полностью удаляются из Room; сессия продолжается для остальных колод; итог фиксируется на настройках

### S19: Краевой случай — невалидное тело ответа

- **GIVEN** Сервер отвечает 200, но тело ответа не соответствует схеме (повреждённый JSON)
- **WHEN** Клиент десериализует ответ
- **THEN** Возникает ошибка десериализации; ответ не применяется; ревизии, признаки и данные не меняются; сессия завершается ошибкой формата на настройках; целостность локальной БД сохранена

### S20: Ошибка синхронизации не влияет на основной функционал

- **GIVEN** Последняя синхронизация завершилась ошибкой (сеть, 400/404/500 или «требуется вход»)
- **WHEN** Пользователь открывает колоды, проходит тренировку, создаёт и редактирует карточки
- **THEN** Все операции выполняются локально без блокировок; изменённые и новые записи получают признак локального изменения и увеличенный счётчик правок — они уйдут на сервер в одной из будущих сессий

### S21: Результат и ошибки видны только на экране настроек

- **GIVEN** Сессия завершилась — успешно или с ошибкой
- **WHEN** Пользователь находится на экранах списка колод или тренировки
- **THEN** Сообщения о синхронизации (снекбары, диалоги, индикаторы) не отображаются; статус, время и ошибки последней синхронизации показываются только на экране настроек

### S22: Редактирование во время выполнения сессии

- **GIVEN** Сессия выполняется; запрос синхронизации потока колоды находится в пути
- **WHEN** Пользователь редактирует карточку этой колоды
- **THEN** UI не блокируется; правка немедленно сохраняется в Room, счётчик правок записи увеличивается, признак локального изменения устанавливается; текущая сессия не затирает правку (срабатывает защита счётчика правок, S10)

### S23: Повторный запуск во время выполнения сессии

- **GIVEN** Сессия синхронизации уже выполняется
- **WHEN** Пользователь нажимает кнопку «Синхронизировать сейчас»
- **THEN** Вторая параллельная сессия не создаётся; текущая продолжается; экран настроек показывает состояние «выполняется»; по завершении фиксируется один итоговый результат

### S24: Возобновление после частично завершённой сессии

- **GIVEN** Предыдущая сессия оборвалась: ревизия колод обновлена до 42, карточки колоды 5 остались на ревизии 7; часть локальных изменений не отправлена
- **WHEN** Запускается новая сессия
- **THEN** `POST /api/v1/sync/decks` отправляется с `since=42`, карточки колоды 5 — с `since=7`; повторное применение ответов не создаёт дублей записей; неотправленные записи входят в отправку повторно

### S25: Краевой случай — серверная запись не применяется, если локальная копия изменена после снапшота

- **GIVEN** В ответе 200 присутствует карточка x7, которой не было в отправке этой сессии; локальная копия x7 помечена как изменённая (правка сделана после снятия снапшота, пока запрос был в пути)
- **WHEN** Клиент применяет ответ
- **THEN** Серверная версия x7 не применяется — локальная правка не затирается (правило specs/API.md, §3.3); x7 остаётся помеченной и уйдёт на сервер следующей сессией, конфликт разрешит сервер по last-write-wins; записи ответа с немаркированными локальными копиями применяются обычно

### S26: Краевой случай — больше 1000 локальных изменений и HTTP 413

- **GIVEN** В потоке 1200 записей, помеченных как локально изменённые
- **WHEN** Выполняется синхронизация потока
- **THEN** Отправка выполняется чанками не более 1000 записей, по мере успеха каждого (лимит specs/API.md, §413); все ответы применяются; ревизия потока принимает значение последнего ответа
- **AND IF** сервер ответил 413 TOO_MANY_CHANGES на слишком крупный массив
- **THEN** Сессия прерывается ошибкой с понятным описанием на экране настроек; признак локального изменения не снимается ни с одной записи; повторная попытка выполняется чанками

## OpenAPI Delta

Изменения контракта API относительно текущего состояния проекта:

```yaml
# openapi-delta
# Контракт синхронизации уже зафиксирован в specs/openapi.yaml + specs/API.md
# (источник истины, своего формата не вводим). Изменение клиентское:
# новые пути и схемы не добавляются, существующие не модифицируются.
# Потребляемые операции (справочно, без правок):
#   POST /api/v1/sync/decks                — дельта-обмен колодами:
#                                     запрос {sinceRevision, changed[]} ->
#                                     ответ {revision, items[], fullSnapshot}
#   POST /api/v1/sync/decks/{deckUuid}/cards — дельта-обмен карточками колоды (формат тот же)
#   POST /api/v1/auth/refresh              — обновление пары access/refresh токенов
paths: {}
components:
  schemas: {}
```
